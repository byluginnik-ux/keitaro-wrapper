# Техническое задание: Keitaro Wrapper

Источник истины для кода и тестов. Каждое требование имеет номер; каждому номеру соответствует тест (раздел 9).

## 1. Цель

Сервис для команды закупки трафика. Две задачи:

1. **Создаватор** — по названию, стране и офферу создаёт в Keitaro готовую кампанию с двумя потоками.
2. **Редактор** — добавляет и удаляет офферы в потоках существующей кампании, пересчитывает доли и публикует изменения в Keitaro по кнопке.

## 2. Границы

Входит: создание кампаний, редактор офферов, справочники Keitaro (домены, группы, источники, офферы, страны), журнал операций.

Не входит: статистика и тренды, лендинги, создание офферов, правка фильтров и редиректов существующих потоков, авторизация пользователей сервиса.

## 3. Словарь

| Термин | Значение |
|--------|----------|
| Кампания | Ссылка в Keitaro с набором потоков. Имеет домен, группу и источник трафика |
| Поток (stream, flow) | Правило внутри кампании: кого ловит и куда отправляет |
| Оффер | Целевая страница рекламодателя, заведённая в Keitaro |
| Доля (share) | Процент трафика потока, уходящий на оффер. Целое число, сумма по потоку — 100 |
| Закрепление (pin) | Доля оффера зафиксирована и не меняется при пересчёте |
| Черновик | Локальные изменения потока, ещё не отправленные в Keitaro |
| Опубликованное состояние | Состав и доли потока, совпадающие с Keitaro на момент последней публикации или загрузки |
| removed | Оффер исключён из потока, но остаётся в нашей базе и может быть возвращён |

## 4. Архитектура

```
браузер ──▶ frontend: Nuxt + Nitro (BFF) ──▶ backend: FastAPI + GraphQL ──▶ Keitaro Admin API
                    │                                   │
                    │                                   └──▶ хранилище: Postgres (SQLAlchemy) | MongoDB
                    └────────▶ contracts: schema.graphql + типы ◀────────┘
```

- **R-ARCH-01.** Репозиторий делится на `backend/`, `frontend/` и `contracts/`. `backend/` и `frontend/` не импортируют код друг друга; обе зависят только от `contracts/`.
- **R-ARCH-02.** Контракт между частями — пакет `contracts/`. Источник истины — `contracts/schema.graphql`: типы Python и TypeScript генерируются из него, и обе части берут их из пакета. Схема бэкенда обязана совпадать со схемой пакета; расхождение роняет тесты.
- **R-ARCH-03.** Бэкенд отдаёт один эндпоинт GraphQL `/graphql` и `/health`.
- **R-ARCH-04.** Браузер обращается только к маршрутам BFF `/api/*`. Адрес бэкенда и ключ Keitaro в браузер не попадают.
- **R-ARCH-05.** BFF не содержит предметной логики и не хранит состояние: собирает данные экрана, проверяет ввод, приводит ошибки к виду `{ code, message, field? }`.
- **R-ARCH-06.** Предметная логика лежит в сервисах бэкенда. Резолвер GraphQL вызывает один метод сервиса.
- **R-ARCH-07.** Расчёт долей — чистая функция без ввода-вывода.
- **R-ARCH-08.** `contracts/` — публикуемая единица: npm-пакет `@keitaro-wrapper/contracts` и пакет Python `keitaro-wrapper-contracts` с одной версией (semver). Удаление или переименование — мажорная версия, добавление — минорная; каждое изменение схемы записано в `contracts/CHANGELOG.md`.
- **R-ARCH-09.** Сгенерированные файлы пакета руками не правятся; CI проверяет, что повторная генерация ничего не меняет.

## 5. Интеграция с Keitaro

Admin API: база `{KEITARO_BASE_URL}/admin_api/v1`, заголовок `Api-Key`. Схема — `https://admin-api.docs.keitaro.io/openapi.json`.

| Действие | Запрос |
|----------|--------|
| Создать кампанию | `POST /campaigns` |
| Создать домен | `POST /domains` (обязательно `name`) |
| Прочитать кампанию | `GET /campaigns/{id}` |
| Удалить кампанию | `DELETE /campaigns/{id}` |
| Создать поток | `POST /streams` |
| Потоки кампании | `GET /campaigns/{id}/streams` |
| Изменить поток | `PUT /streams/{id}` |
| Справочники | `GET /offers`, `GET /domains`, `GET /groups?type=campaigns`, `GET /traffic_sources` |

- **R-KT-01.** Клиент типизирован: ответы разбираются в модели, неизвестные поля не ломают разбор.
- **R-KT-02.** Ошибки Keitaro (4xx, 5xx, таймаут, неразборчивый ответ) превращаются в одно исключение `KeitaroError` с кодом и текстом.
- **R-KT-03.** Запросы на чтение при сбое сети и 5xx повторяются до трёх раз. Запросы на запись не повторяются.
- **R-KT-04.** Ключ читается из окружения, не пишется в журнал и не возвращается наружу.

Значения сверены с живым трекером; обезличенные ответы лежат в `backend/tests/fixtures/keitaro/`.

| Поток | `type` | `schema` | `action_type` | `action_payload` | `filters` | `offers` |
|-------|--------|----------|---------------|------------------|-----------|----------|
| 1, редирект | `regular` | `redirect` | `http` | `https://google.com` | `[{name: "country", mode: "accept", payload: ["AU"]}]` | — |
| 2, офферы | `regular` | `landings` | `http` | пусто | — | `[{offer_id, share, state: "active"}]` |

- **R-KT-05.** Keitaro не проверяет сумму долей потока: загруженные доли принимаются как есть, даже если их сумма не равна 100; пересчёт происходит при первом изменении состава.
- **R-KT-06.** Запрос несуществующей сущности возвращает 404 со страницей HTML, а не JSON; клиент превращает его в `KeitaroError` без попытки разбора.
- **R-KT-07.** Поиск офферов выполняется на бэкенде по названию и ID над полным списком `GET /offers` (Keitaro поиск не предоставляет); список кэшируется на короткий срок.

## 6. Создаватор кампаний

Вход: название, код страны, ID оффера, домен (существующий или имя нового), группа, источник трафика.

- **R-CR-01.** Название обязано начинаться с префикса из `CAMPAIGN_NAME_PREFIX` (`test_bulygin_`) и содержать после него хотя бы один символ.
- **R-CR-02.** Код страны — ISO 3166-1 alpha-2 из встроенного списка; регистр не важен, в Keitaro уходит в верхнем.
- **R-CR-03.** Оффер, группа и источник должны существовать в Keitaro; домен — существовать либо быть задан именем для создания (R-CR-10). Иначе отказ с указанием поля.
- **R-CR-04.** Создаётся кампания с выбранными доменом, группой и источником.
- **R-CR-05.** Поток 1: принимает посетителей из указанной страны (фильтр страны, режим accept) и перенаправляет на `https://google.com`.
- **R-CR-06.** Поток 2: идёт после первого, без фильтров, отправляет на выбранный оффер с долей 100.
- **R-CR-07.** Если создание кампании окончательно не удалось после того, как кампания появилась в Keitaro, она удаляется; задача завершается отказом с причиной. Полусобранных кампаний не остаётся. Если удалить не удалось, в причине назван ID кампании, которую нужно удалить вручную.
- **R-CR-08.** Успешно созданная кампания и её потоки сохраняются в хранилище в одной транзакции с итогом задачи; задача несёт наш ID кампании.
- **R-CR-09.** Операция записывается в журнал: кто-что-когда, результат, ID в Keitaro.
- **R-CR-10.** Вместо существующего домена пользователь может задать имя нового: домен создаётся в Keitaro (`POST /domains`) до кампании, и кампания привязывается к нему.
- **R-CR-11.** Имя нового домена — имя хоста без схемы и пути, в нижнем регистре. Если домен с таким именем уже есть в Keitaro, используется он, новый не создаётся.
- **R-CR-12.** Если домен создан, а кампания или поток — нет, домен не удаляется: он остаётся в справочнике, а в ошибке сказано, что домен создан. Сбой создания домена прерывает операцию до создания кампании.
- **R-CR-13.** Запрос на создание проверяет форму (R-CR-01…03, 11) и, если замечаний нет, только ставит задачу `create_campaign`: в Keitaro пишет обработчик. Замечания по полям возвращаются сразу, задача при них не ставится. ID задачи выдаёт клиент (R-TK-04).
- **R-CR-14.** Обработчик выполняет шаги по порядку — домен, кампания, поток 1, поток 2 — и отмечает сделанное в задаче. Повторная доставка продолжает с несделанного и не создаёт дублей: домен ищется по имени, кампания — по alias, выбранному при постановке задачи, потоки — по позиции в кампании.
- **R-CR-15.** Сбой сети и ответ 5xx — повод для новой попытки; отказ 4xx, исчерпание попыток и сообщение из очереди отказов завершают задачу отказом с компенсацией по R-CR-07 и R-CR-12. Итог публикуется событием `campaign.created` или `campaign.create.rejected` в одной транзакции с записью итога.

## 7. Редактор офферов

### 7.1 Модель

Привязка «оффер в потоке» хранит: ID оффера и его название, долю, признак закрепления, статус (`active` | `removed`) и опубликованный снимок (доля, статус, закрепление, был ли оффер опубликован). Поток имеет признак `dirty` — есть ли неопубликованные изменения.

### 7.2 Загрузка из Keitaro

- **R-ED-01.** «Загрузить потоки» забирает все потоки кампании и сохраняет их локально.
- **R-ED-02.** Поток без офферов показывается как поток без содержимого: фильтры и редирект не разбираются и не отображаются.
- **R-ED-03.** Офферы потока из Keitaro сохраняются со своими долями в статусе `active`; это опубликованное состояние.
- **R-ED-04.** Оффер, известный нам, но отсутствующий в Keitaro при повторной загрузке, не удаляется, а получает статус `removed` и долю 0.
- **R-ED-05.** Закрепления при повторной загрузке сохраняются, если доля в Keitaro равна закреплённой; иначе закрепление снимается.
- **R-ED-06.** Загрузка при наличии черновика в любом потоке кампании отклоняется (`DraftNotPublished`), пока черновик не опубликован или не отменён.
- **R-ED-07.** Кампания задаётся её ID в Keitaro. Если в нашей базе её нет, она читается из Keitaro и сохраняется; так в редактор попадает кампания, созданная не через создаватор. Неизвестный ID — отказ `CampaignNotFound`.
- **R-ED-08.** Поток, которого при повторной загрузке в Keitaro уже нет, удаляется и из нашей базы.

### 7.3 Черновик

- **R-ED-10.** Добавление оффера: оффер выбирается поиском по офферам Keitaro, появляется в потоке со статусом `active`, доли пересчитываются, поток становится `dirty`. В Keitaro ничего не меняется.
- **R-ED-11.** Добавление оффера, уже активного в потоке, отклоняется (`OfferAlreadyInStream`). Добавление оффера в статусе `removed` равно возврату (R-ED-13).
- **R-ED-12.** Удаление: оффер получает статус `removed` и долю 0, закрепление снимается, доли остальных пересчитываются, поток становится `dirty`. Оффер, ни разу не опубликованный, при удалении исчезает из потока: возвращать в Keitaro нечего.
- **R-ED-13.** Возврат: оффер в статусе `removed` снова становится `active`, доли пересчитываются, поток становится `dirty`.
- **R-ED-14.** Отмена: поток возвращается к опубликованному снимку. Офферы, ни разу не опубликованные, исчезают из потока; остальные получают опубликованные долю, статус и закрепление. `dirty` снимается.
- **R-ED-15.** Если после изменения черновик совпал с опубликованным снимком, `dirty` снимается.
- **R-ED-16.** Офферы добавляются только в поток со схемой `landings`; для потока-перенаправления действие отклоняется.

### 7.4 Публикация

Публикация — задача (раздел 13): запрос ставит её и сразу отвечает, в Keitaro пишет обработчик.

- **R-ED-20.** «Опубликовать» ставит задачу публикации с составом потока: только офферы `active` с их долями. Обработчик отправляет этот состав в Keitaro.
- **R-ED-21.** После успеха текущее состояние становится опубликованным снимком, `dirty` снимается, задача получает статус `succeeded`. Офферы `removed` остаются в нашей базе.
- **R-ED-22.** При отказе Keitaro черновик сохраняется без изменений, поток остаётся `dirty`, задача получает статус `rejected` с причиной, пользователь видит причину.
- **R-ED-23.** Публикация потока без активных офферов отклоняется сразу (`EmptyStream`), задача не ставится.
- **R-ED-24.** Каждая публикация записывается в журнал с составом «до» и «после» — в той же транзакции, что и её итог.
- **R-ED-25.** Пока задача публикации не завершена, поток занят: правки, отмена, повторная публикация и загрузка из Keitaro отклоняются (`StreamBusy`). Завершение задачи освобождает поток.
- **R-ED-26.** Публикация потока без изменений ничего не отправляет: задача сразу `succeeded`.

### 7.5 Доли

Пересчёт выполняется после каждого изменения состава или закреплений.

- **R-SH-01.** Доли — целые числа от 0 до 100. Сумма долей активных офферов потока равна 100.
- **R-SH-02.** Доля оффера в статусе `removed` равна 0.
- **R-SH-03.** Закреплённая доля при пересчёте не меняется.
- **R-SH-04.** Остаток `100 − Σ закреплённых` делится между незакреплёнными активными офферами поровну с округлением вниз; нераспределённые единицы раздаются по одной первым по порядку. Примеры: `100 / 3 → 34, 33, 33`; `75 / 2 → 38, 37`.
- **R-SH-05.** Порядок офферов — порядок добавления в поток; для загруженных из Keitaro — порядок в ответе Keitaro.
- **R-SH-06.** Закрепление с вводом значения: пользователь задаёт долю от 1 до 100, она закрепляется, остальные пересчитываются.
- **R-SH-07.** Снятие закрепления запускает пересчёт с участием этого оффера.
- **R-SH-08.** Отказ `ShareOverflow`, если Σ закреплённых > 100; если Σ закреплённых = 100 и есть незакреплённые активные; если все активные закреплены и Σ ≠ 100. Состояние при отказе не меняется.
- **R-SH-09.** Незакреплённый активный оффер не может получить долю 0: если остаток меньше числа незакреплённых — отказ `ShareOverflow`.

### 7.6 Приёмочные сценарии

Исходное состояние для сценариев: кампания в Keitaro с двумя потоками. Поток 1 — редирект на Google по стране. Поток 2 — офферы A, B, C с долями 34, 33, 33.

**S1. Загрузка.** Когда пользователь нажимает «Загрузить потоки», то видит два потока: поток 1 без содержимого, поток 2 с A 34 %, B 33 %, C 33 %; оба не `dirty`.

**S2. Добавление.** Дано S1. Когда пользователь находит оффер D и добавляет его в поток 2, то доли становятся 25, 25, 25, 25, поток `dirty`, в Keitaro по-прежнему три оффера.

**S3. Публикация.** Дано S2. Когда пользователь нажимает «Опубликовать» и задача публикации выполнена, то в Keitaro поток 2 содержит A, B, C, D по 25 %, поток не `dirty`.

**S4. Отмена.** Дано S2. Когда пользователь нажимает «Отменить», то в потоке 2 снова A 34 %, B 33 %, C 33 %, оффера D нет, поток не `dirty`.

**S5. Удаление и возврат.** Дано S3. Когда пользователь удаляет B, то B получает статус `removed` и 0 %, остальные 34, 33, 33, поток `dirty`. После публикации B нет в Keitaro, у нас B остаётся `removed` с действием «Вернуть». Когда пользователь возвращает B и публикует, то B снова в Keitaro, доли 25, 25, 25, 25.

**S6. Изменение в Keitaro.** Дано S3. Когда в админке Keitaro из потока 2 удалены C и D и пользователь снова нажимает «Загрузить потоки», то у нас A и B активны с долями из Keitaro, C и D — `removed` с 0 %.

**S7. Закрепление.** Дано: в потоке A, B, C активны, D `removed`. Когда пользователь закрепляет у C долю 25 % и возвращает D, то C остаётся 25 %, а A, B, D получают 25, 25, 25. Когда затем удаляет D, то C остаётся 25 %, A и B получают 38 и 37.

**S8. Переполнение.** Дано: A закреплён на 60 %. Когда пользователь закрепляет B на 50 %, то получает отказ `ShareOverflow`, доли не меняются.

## 8. Интерфейс

### 8.1 Создаватор

- **R-UX-01.** Одна форма. Поле названия содержит неизменяемый префикс; пользователь вводит только продолжение.
- **R-UX-02.** Страна выбирается поиском по названию и коду. Оффер, домен, группа, источник — списками с поиском; справочники приходят одним запросом к BFF.
- **R-UX-05.** В списке доменов введённое имя, которого нет среди существующих, предлагается пунктом «Создать домен …». Выбранный к созданию домен помечен как новый; создаётся он только при отправке формы.
- **R-UX-06.** После отправки форма показывает «Создаётся…» и шаги задачи; по завершении — итог по R-UX-04. Отказ показывается рядом с формой вместе с причиной, введённое сохраняется.
- **R-UX-03.** Ошибки показываются у поля, к которому относятся; общая ошибка Keitaro — над формой.
- **R-UX-04.** После успеха — ссылки «Открыть в Keitaro» и «В редактор».

### 8.2 Редактор

- **R-UX-10.** На потоке видны: название, признак «Не опубликовано», шкала долей, список офферов с долями.
- **R-UX-11.** Состояние не передаётся одним цветом: `dirty` — полоса акцента и текстовая метка; `removed` — приглушённая строка и метка; закрепление — значок с подписью для экранного чтения.
- **R-UX-12.** У изменённой доли показано «было → стало».
- **R-UX-13.** Панель «Опубликовать / Отменить» закреплена внизу потока и показывает число изменений; видна только у `dirty`.
- **R-UX-14.** Доля правится на месте: Enter — закрепить значение, Esc — отменить ввод.
- **R-UX-15.** Все действия доступны с клавиатуры; порядок фокуса совпадает с визуальным.
- **R-UX-16.** Оформлены состояния: загрузка, пустая кампания, поток без офферов, ошибка Keitaro. Ошибка не стирает черновик.
- **R-UX-18.** После «Опубликовать» поток показывает «Публикуется…», его действия закрыты; когда задача завершена, поток показывает итог: опубликованное состояние или причину отказа с сохранённым черновиком. Открытая заново страница продолжает следить за незавершённой публикацией.
- **R-UX-17.** Если поток изменили в другом окне, действие не применяется: на месте потока появляется его актуальное состояние и сообщение об этом.

### 8.3 Общее

- **R-UX-30.** Страница «Задачи»: сводка очереди (задачи по статусам, неотправленные сообщения, очереди и обработчики; «обработчиков нет» — предупреждением) и список задач с видом, статусом, числом попыток, временем, причиной отказа и шагами; отбор по статусу.

- **R-UX-32.** Страница обновляется сама, пока она открыта, и по кнопке; сбой обновления не стирает показанное.
- **R-UX-20.** Светлая и тёмная темы; выбор по настройке системы с ручным переключателем.
- **R-UX-21.** Вёрстка работает от 360 px до сверхшироких экранов без горизонтальной прокрутки.
- **R-UX-22.** Контраст текста и элементов управления — не ниже WCAG AA.

## 9. Хранилище

- **R-ST-01.** Сервисы работают с хранилищем через интерфейсы (`Protocol`), не зная реализации.
- **R-ST-02.** Реализация по умолчанию — PostgreSQL через SQLAlchemy (async); схема меняется только миграциями Alembic.
- **R-ST-03.** Вторая реализация — MongoDB. Выбор — переменной `STORAGE_BACKEND=postgres|mongo` при старте. Третье значение, `memory`, держит данные в памяти процесса — для тестов сервисов и запуска без базы.
- **R-ST-04.** Обе реализации проходят один и тот же набор контрактных тестов.
- **R-ST-05.** Изменение потока и его привязок атомарно: либо применяется целиком, либо не применяется.
- **R-ST-06.** Всё, что записывает одно действие сервиса (кампания, потоки, журнал), — одна транзакция хранилища: при сбое не остаётся ничего. Нарушения целостности хранилище сообщает типами: «запись устарела», «дубль», «нет владельца».

Сущности: кампания, поток, привязка оффер–поток, запись журнала.

Приняты там, где задание и видео-образец молчат. Меняются правкой этого раздела и соответствующего требования.

1. Домен, группу и источник пользователь выбирает в форме; задание называет входом только название, страну и оффер (R-CR-03). Домен можно выбрать из существующих или создать сразу в форме (R-CR-10…12, решение заказчика).

5. Удаление оффера снимает его закрепление (R-ED-12).

## 13. Нагрузка и надёжность

Сервис рассчитан на несколько одновременных пользователей и несколько процессов бэкенда.

Изменения в Keitaro выполняются **задачами**: запрос пользователя ставит задачу и сразу получает её в ответ, работу делает отдельный обработчик, итог задачи — событие «выполнено» или «отказано».

### 13.1. Конкурентная запись

- **R-CC-01.** У потока есть версия — целое число; каждая запись потока увеличивает её на 1.
- **R-CC-02.** Запись потока условная: применяется, только если версия в хранилище равна версии, с которой поток был прочитан. Иначе запись отклоняется и ничего не меняет.
- **R-CC-03.** Одновременные правки одного потока: каждая либо применяется, либо получает отказ `StreamConflict`. Потерянных правок нет; сумма долей активных офферов остаётся 100.
- **R-CC-04.** Одновременные загрузки одной кампании сходятся к одной кампании и одному набору потоков: наши ID кампании и потока выводятся из их ID в Keitaro.
- **R-CC-05.** Загрузка не затирает черновик, появившийся, пока шёл запрос к Keitaro: она отклоняется как при R-ED-06.
- **R-CC-06.** Поток отдаётся клиенту вместе с версией. Действие над потоком несёт версию, которую видел пользователь (`expectedVersion`); если поток с тех пор изменился, действие не применяется, ответ — `StreamConflict` с актуальным потоком. Без `expectedVersion` действие применяется к тому, что сохранено сейчас.

### 13.2. Задачи

- **R-TK-01.** Задача хранит: ID, вид (`publish_stream` | `create_campaign`), статус, запрос, с которым её поставили, и его отпечаток, число попыток, шаги с временем, итог или причину отказа, время постановки, начала и завершения, ссылки на кампанию и поток.
- **R-TK-02.** Статусы: `pending` → `running` → `succeeded` | `rejected`; `pending` → `cancelled`. Переход условный: применяется, только если задача сейчас в ожидаемом статусе. Из двух одновременных переходов проходит один.
- **R-TK-03.** ID задачи выдаёт клиент, он же ключ идемпотентности: вторая задача с тем же ID не создаётся.

- **R-TK-04.** Повтор запроса с тем же ID задачи возвращает уже поставленную задачу в её текущем статусе и ничего не делает второй раз. Тот же ID с другим запросом отклоняется (`TaskKeyReused`).
- **R-TK-05.** Задачу можно прочитать по ID: статус, попытки, шаги, причина отказа.
- **R-TK-06.** Список задач: сначала новые, с отбором по статусам и виду и с ограничением числа.
- **R-TK-07.** Состояние очереди читается одним запросом: число задач в каждом статусе, число неотправленных исходящих сообщений и время самого старого из них, по каждой очереди шины — сколько сообщений ждёт и сколько обработчиков слушает.
- **R-TK-08.** Отменить можно только задачу в статусе `pending`: она становится `cancelled`, поток освобождается, черновик остаётся — одной транзакцией. Задача в другом статусе не отменяется (`TaskNotCancellable`). Обработчик, получив сообщение отменённой задачи, ничего не делает.
- **R-TK-09.** Повторить можно только отклонённую задачу: ставится новая задача с ID от клиента и ссылкой на исходную (`retryOf`). Для публикации публикуется текущий черновик потока; для создания кампании исходный запрос проверяется заново. Отказы — те же, что у исходного действия. Задача в другом статусе и задача без сохранённого запроса не повторяются (`TaskNotRetryable`).

### 13.3. События

- **R-EV-01.** Сообщение о поставленной задаче и о её итоге записывается в таблицу исходящих (outbox) в той же транзакции, что и изменение данных: либо есть и то и другое, либо ничего.
- **R-EV-02.** Исходящие сообщения забирает отправитель: пачкой, в порядке записи, с арендой на время отправки. Два отправителя не берут одно сообщение одновременно; сообщение с истёкшей арендой берётся снова; отправленное больше не выдаётся.
- **R-EV-03.** Отправитель публикует сообщения в шину в порядке записи и помечает сообщение отправленным только после подтверждения шины. Сбой шины сообщение не теряет: оно уходит при следующем проходе. Доставка — «не меньше одного раза».
- **R-EV-04.** Шина выбирается переменной `MESSAGE_BUS=memory|rabbitmq`; обе реализации проходят один набор тестов. В RabbitMQ очереди и сообщения устойчивые, публикация идёт с подтверждением издателя, обработка подтверждается вручную после работы обработчика.
- **R-EV-05.** Сообщение попадает в очередь по теме; очередь получает только свои темы. Сообщение, опубликованное до запуска обработчика, дожидается его.
- **R-EV-06.** Если обработчик упал, сообщение доставляется снова с задержкой и номером попытки. После предельного числа попыток (настройка) оно уходит в очередь отказов этой очереди.
- **R-EV-07.** Обработчик задачи идемпотентен: повторная доставка сообщения завершённой задачи ничего не делает; повторная доставка после обрыва (запись в Keitaro прошла, итог не записан) доводит задачу до того же итога.
- **R-EV-08.** Сбой сети и ответ Keitaro 5xx — повод для новой попытки; отказ 4xx и исчерпание попыток завершают задачу отказом с причиной. Сообщение из очереди отказов тоже завершает свою задачу отказом: задача не остаётся висеть.
- **R-EV-09.** Итог задачи публикуется событием: `stream.published` или `stream.publish.rejected` — в той же транзакции, что и запись итога.

### 13.4. Эксплуатация

- **R-OPS-01.** Стек `docker compose up` работает через RabbitMQ: веб-процесс только ставит задачи, отправитель outbox (`relay`) и обработчик (`worker`) — отдельные процессы из того же образа.
- **R-OPS-02.** Обработчиков может быть несколько (`--scale worker=N`): задачу выполняет один из них, страница «Задачи» показывает их число. Остановленный обработчик задач не теряет: они ждут в очереди и выполняются после его запуска.
- **R-OPS-03.** Процессы завершаются по SIGTERM без потери взятого сообщения: неподтверждённое возвращается в очередь.
- **R-OPS-04.** `GET /health/ready` бэкенда отвечает 200, только когда доступны хранилище, шина и кэш; иначе 503 и названия недоступных частей (`storage`, `bus`, `cache`). Каждая проверка ограничена по времени. `GET /health` остаётся проверкой «процесс жив» и от зависимостей не зависит. Compose считает бэкенд здоровым по `/health/ready`.
- **R-OPS-05.** Размеры пулов задаются переменными: `DB_POOL_SIZE`, `DB_MAX_OVERFLOW`, `MONGO_MAX_POOL_SIZE`, `RABBITMQ_PREFETCH` (сколько сообщений обработчик берёт одновременно).
- **R-OPS-06.** Нагрузочный сценарий (`backend/scripts/load.py`) работает на стеке с поддельным трекером (`compose.load.yaml`) через BFF: готовит N кампаний с черновиками, одновременно ставит N публикаций и K созданий кампаний, каждый запрос повторяет с тем же `taskId`, на время включает сбой трекера и ждёт конца всех задач. Сценарий завершается с ошибкой, если: осталась незавершённая задача; задач появилось не столько, сколько уникальных `taskId`; у выполненного создания в трекере не ровно одна кампания, у отклонённого — есть хоть одна; сумма долей потока в трекере не 100; выполненная публикация не довела оффер до трекера; в outbox остались сообщения. Печатает число задач, время, задач в секунду, медиану и 95-й перцентиль времени от постановки до итога.

### 13.5. Кэш справочников

- **R-CH-01.** Справочники Keitaro — домены, группы, источники, активные офферы — читаются через кэш со сроком жизни (`CATALOG_TTL`, секунды). Проверка формы создания читает трекер напрямую: отказ опирается на свежие данные.
- **R-CH-02.** Кэш выбирается переменной `CACHE_BACKEND=memory|redis`; обе реализации проходят один набор тестов. С Redis кэш общий для всех процессов.
- **R-CH-03.** При пустом кэше одновременные запросы одного справочника делают одно обращение к Keitaro: загружает тот, кто взял замок, остальные ждут значение. Замок имеет срок: если владелец пропал, загрузку берёт следующий. Упавшая загрузка в кэш ничего не кладёт.

- **R-CH-05.** После создания домена список доменов в кэше сбрасывается.
