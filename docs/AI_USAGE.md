# Использование ИИ-агентов

Журнал для ответа на вопрос формы сдачи. Пополняется по ходу работы.

## Подход

- Агент — Claude Code. Работает от технического задания (`docs/SPEC.md`): требование → падающий тест → реализация.
- Правила для агента лежат в репозитории: `AGENTS.md` в корне и в каждой части, скиллы в `.agents/skills/`. Агент бэкенда и агент фронта получают разные наборы скиллов.
- Человек принимает решения об архитектуре, утверждает ТЗ и план, проверяет результат на живом Keitaro.

## Журнал

| Этап | Что делал агент | Что решал человек |
|------|-----------------|-------------------|
| Разбор задания | Снял логику редактора с видео-образца (субтитры и кадры), выписал поля Admin API из OpenAPI-схемы Keitaro | Стек фронта, хранилище, GraphQL, BFF на Nitro, деление на две части |
| ТЗ и список фич | Составил `SPEC.md` с нумерованными требованиями и сценариями, `FEATURES.md` с порядком работ | Утверждение плана |
| Папки агентов | Написал проектные скиллы и правила для обеих частей | Состав скиллов и их деление по частям |
| Клиент Keitaro, расчёт долей | Тесты на эталонных ответах трекера, затем клиент; таблица случаев и property-тесты, затем чистая функция долей | Ключ Admin API, запрет записи в трекер до финальной проверки |
| Контракты | Вынес схему GraphQL в `contracts/`, настроил генерацию типов Python и TypeScript и проверку «сгенерированное свежо» | Решение сделать контракты отдельным публикуемым пакетом и единой точкой правки |
| Хранилище | Один контрактный набор тестов, три адаптера: память, SQLAlchemy + Alembic, MongoDB | Требование переключать Postgres ↔ Mongo |
| Редактор (бэкенд) | Сценарии S1–S8 из ТЗ переписал тестами дословно; сверка с Keitaro, черновик, публикация; отказы — типами union, а не строками | Логика редактора по видео-образцу, допущения раздела 12 |
| Создаватор (бэкенд) | Правка контракта → красные тесты R-CR-01…12 → сервис с откатом кампании при сбое → мутация | Правило «домен выбирается или создаётся сразу» |
| BFF | Запросы GraphQL с кодогенерацией типов, маршруты экранов, приведение отказов к одному виду `{code, message, fields}` | Требование «фронт ходит только в свой сервер» |
| Дизайн-система | Токены для двух тем, тест контраста числом, базовые компоненты с проверкой по ролям и подписям | Выбор стиля, темы по системе с ручным переключателем |
| Форма создаватора | Поддельный Keitaro по HTTP, чтобы смотреть интерфейс и не писать в живой трекер; форма и её тесты; снимки страницы в двух темах и на 360 px | Замечание, что Nitro — часть Nuxt, а не третий сервис (уточнены документы) |
| Редактор потоков | Тест на каждое состояние из таблицы состояний, затем компоненты; сквозные сценарии S1–S8 в Playwright на всём сервисе с поддельным трекером. Сквозной тест с клавиатуры нашёл потерю фокуса после запроса — исправлено | Логика редактора, приёмочные сценарии |
| Проверка перед сдачей | Сборка compose на Postgres и MongoDB, чтение справочников с живого трекера, Lighthouse (доступность 100 на трёх страницах), ограничения GraphQL от требования R-Q-07 | Запись в живой Keitaro и публикация репозитория — только по слову человека |

## Ответ для формы сдачи

Работал с Claude Code как с исполнителем по техническому заданию. Сначала вместе с агентом составил `docs/SPEC.md`: нумерованные требования и приёмочные сценарии S1–S8, логику редактора агент снял с видео-образца. Дальше каждая фича шла одним порядком: требование → коммит с падающим тестом → коммит с реализацией → строка в матрице «требование → тест». Этот порядок записан в `AGENTS.md` и в скиллах (`.agents/skills/`), у бэкенда, фронта и контрактов свои наборы правил — агент читает их сам.

Что решал я: архитектуру (GraphQL на FastAPI, BFF на серверной части Nuxt, контракты отдельным пакетом, переключаемое хранилище), допущения там, где задание молчит, и всё, что необратимо: запись в живой Keitaro, публикацию. Что делал агент: код, тесты, миграции, CI, проверку интерфейса в браузере.

Что это дало: сценарии из ТЗ переписаны тестами дословно и идут на трёх уровнях (сервис, GraphQL, браузер); настоящий трекер тесты не трогают — вместо него поддельный с тем же контрактом. Ошибки, которые нашли проверки, а не чтение кода: потеря фокуса клавиатуры после запроса, выбор из устаревшего списка поиска, расхождение имени поля `schema` на проводе.
