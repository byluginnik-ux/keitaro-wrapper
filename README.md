# Keitaro Wrapper

Обёртка над рекламным трекером Keitaro: создание кампаний с двумя потоками и редактор офферов в потоках с черновиком, пересчётом долей и публикацией в трекер.

- [Запуск](#запуск) · [Соответствие заданию](#соответствие-заданию) · [Архитектура](#архитектура) · [Что готово](#что-готово) · [Разработка](#разработка)
- **Видео, 2,5 минуты:** [создаватор и редактор на живом Keitaro](https://github.com/byluginnik-ux/keitaro-wrapper/releases/download/demo-v2/keitaro-wrapper-demo.mp4); сценарий записи — [demo/](demo/README.md).
- Техническое задание — [docs/SPEC.md](docs/SPEC.md); архитектура подробно — [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md); порядок показа — [docs/DEMO.md](docs/DEMO.md); как использовались ИИ-агенты — [docs/AI_USAGE.md](docs/AI_USAGE.md).

## Запуск

### С настоящим Keitaro

Нужен Docker с Compose и ключ Admin API.

```
cp .env.example .env        # вписать KEITARO_API_KEY из админки Keitaro
docker compose up --build
```

Интерфейс — http://127.0.0.1:3000 (порт меняется переменной `FRONTEND_PORT`). Миграции базы применяются сами до старта бэкенда. Бэкенд наружу не открыт: к нему обращается только BFF.

Стек работает через RabbitMQ: `backend` ставит задачи, `relay` отправляет сообщения из outbox в шину, `worker` выполняет задачи в Keitaro. Обработчиков может быть несколько: `docker compose up --build --scale worker=2`; их число и состояние очереди видны на странице «Задачи».

Сервис создаёт кампании только с префиксом `test_bulygin_` (`CAMPAIGN_NAME_PREFIX`).

### Без Keitaro и без Docker

Трекер заменяет поддельный из тестов, данные живут в памяти. Нужны `uv` и Node.js с corepack. Три терминала:

```
# 1. поддельный трекер
cd backend && uv sync
uv run uvicorn tests.fake_tracker:app --port 8791

# 2. бэкенд
cd backend
KEITARO_BASE_URL=http://127.0.0.1:8791 KEITARO_API_KEY=fake-key STORAGE_BACKEND=memory \
  uv run uvicorn --factory app.main:create_app --port 8792

# 3. интерфейс
cd frontend && corepack pnpm install
NUXT_BACKEND_GRAPHQL_URL=http://127.0.0.1:8792/graphql corepack pnpm dev
```

Интерфейс — http://localhost:3000. Готовую кампанию с двумя потоками для редактора создаёт команда ниже; `campaignId` из ответа вводится на главной странице.

```
curl -X POST http://127.0.0.1:8791/__test/campaign -H 'content-type: application/json' -d '{}'
```

### Страницы

| Страница | Что на ней |
|----------|------------|
| `/` | Кампании сервиса; открыть любую кампанию трекера по её ID |
| `/create` | Создаватор: название с префиксом, страна, оффер, домен (существующий или новый), группа, источник. Создаёт кампанию и два потока: первый уводит выбранную страну на Google, второй ведёт на оффер. При сбое кампания удаляется |
| `/campaigns/<id>` | Редактор офферов в потоках: добавить, удалить, вернуть, закрепить долю. Изменения копятся в черновике и уходят в Keitaro кнопкой «Опубликовать»; «Отменить» возвращает опубликованное состояние |

### Переменные окружения

| Переменная | По умолчанию | Назначение |
|------------|--------------|------------|
| `KEITARO_BASE_URL` | `https://tlgk.host` | адрес трекера |
| `KEITARO_API_KEY` | — | ключ Admin API; без него бэкенд не стартует |
| `CAMPAIGN_NAME_PREFIX` | `test_bulygin_` | обязательный префикс имён кампаний |
| `STORAGE_BACKEND` | `postgres` | `postgres`, `mongo` или `memory` |
| `FRONTEND_PORT` | `3000` | порт интерфейса на хосте |
| `DEBUG` | `false` | GraphiQL и интроспекция схемы на `/graphql` бэкенда |

## Соответствие заданию

Проверено 17.11.2026 прогоном `demo/record.mjs` на живом Keitaro в полном составе стека (RabbitMQ, Redis, отправитель, два обработчика, два веб-процесса). Сценарий ведёт интерфейс в браузере и после каждого шага сравнивает ответ Admin API с ожидаемым; все 17 сверок сошлись, тестовая кампания удалена. Этот прогон и есть видео.

| Пункт задания | Что сверено в Admin API и на странице |
|---------------|----------------------------------------|
| Создаватор принимает название, страну и ID оффера | кампания есть в трекере под своим именем |
| Настроены домен, группа и источник из API | `domain_id`, `group_id`, `traffic_source_id` равны выбранным в форме |
| Поток 1 ловит всех из страны и ведёт на Google | фильтр `country accept KZ`, перенаправление на `https://google.com` |
| Поток 2 ведёт на выбранный оффер | один оффер, доля 100 |
| Редактор добавляет офферы | черновик трекер не меняет; после «Опубликовать» в трекере три оффера, 34 / 33 / 33 |
| Редактор удаляет офферы | после публикации оффера в трекере нет, остальные 50 / 50; «Вернуть» и публикация — он снова там |
| Цифры верные | сумма всегда 100; закреплённые 60 % не меняются при пересчёте; 60 + 50 отклонено, доли прежние |
| Отмена | поток вернулся к опубликованному, в трекер ничего не ушло |
| Состав изменили в самом Keitaro | после «Обновить из Keitaro» убранный оффер помечен «Удалён», доли как в трекере |

Отличия от буквы задания:

- Имя кампании начинается с `test_bulygin_` — ограничение общего трекера; префикс задаётся `CAMPAIGN_NAME_PREFIX`.
- Домен, группа и источник выбираются в форме из справочников Admin API, а не подставляются молча.
- Офферы добавляются только в поток с офферами; поток-перенаправление показан без содержимого и не меняется.
- Нажатие на долю открывает ввод значения; введённая доля закрепляется.
- Создание и публикация выполняются задачами: интерфейс показывает «Создаётся…» и «Публикуется…», затем итог.
- Порядок офферов внутри потока определяет Keitaro: возвращённый оффер он ставит последним.

Отказ создания с удалением начатой кампании на живом трекере не проверялся (пришлось бы ломать создание в общем трекере) — он покрыт тестами и сквозным сценарием на поддельном трекере.

## Архитектура

```
браузер ──▶ frontend: Nuxt + Nitro (BFF) ──▶ backend: FastAPI + GraphQL ──▶ Keitaro Admin API
                    │                                   │
                    │                                   └──▶ хранилище: Postgres | MongoDB
                    └────────▶ contracts: schema.graphql + типы ◀────────┘
```

- `contracts/` — контракт GraphQL: `schema.graphql` и сгенерированные из него типы Python и TypeScript. Собирается в npm-пакет и пакет Python; единственное место правки общих типов.
- `backend/` — FastAPI, GraphQL (Strawberry), SQLAlchemy + Alembic; второй адаптер хранилища — MongoDB. Вся предметная логика здесь: слои `graphql → services → порты хранилища | шлюз Keitaro`.
- `frontend/` — Nuxt (Vue 3 + TypeScript). Nitro — серверная часть самого Nuxt, а не отдельный сервис: маршруты `frontend/server/api/*` работают в том же процессе, что и страницы, и служат BFF между браузером и бэкендом. Логики в BFF нет.

Основные решения:

- **Черновик и снимок.** Поток хранит текущие значения и снимок того, что лежит в Keitaro; «не опубликовано» вычисляется сравнением. Удалённый оффер остаётся со статусом `removed` и долей 0.
- **Доли** считает чистая функция: закреплённые сохраняются, остаток делится поровну, сумма всегда 100.
- **Хранилище за портом.** Postgres, MongoDB и память проходят один набор контрактных тестов; выбор — переменной `STORAGE_BACKEND`.
- **Конкурентная запись.** У потока есть версия, запись условная; правка из устаревшего окна получает отказ с актуальным потоком. Одно действие — одна транзакция вместе с журналом.
- **Событийная запись.** Публикация потока — задача с ключом идемпотентности: запрос пишет задачу и сообщение в outbox одной транзакцией, отправитель передаёт его в шину (память или RabbitMQ), обработчик пишет в Keitaro и фиксирует итог. Сбой трекера — повтор с задержкой, затем отказ с причиной.

Схемы, слои и модель подробно — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

Публикация потока — задача: запрос ставит её и сразу отвечает, в Keitaro пишет обработчик, интерфейс показывает «Публикуется…» и итог. Создание кампании — тоже задача: запрос проверяет форму и ставит её, обработчик создаёт домен, кампанию и потоки по шагам, отмечая сделанное; повторная доставка продолжает с несделанного, при окончательном отказе кампания удаляется. По умолчанию шина работает в памяти процесса (`MESSAGE_BUS=memory`); с `MESSAGE_BUS=rabbitmq` отправитель outbox и обработчик запускаются отдельными процессами: `python -m app.relay`, `python -m app.worker`.

## Миграции

Схема базы меняется только миграциями Alembic (`backend/alembic/versions/`). При `docker compose up` их применяет сервис `migrate` до старта бэкенда. Вручную:

```
docker compose run --rm migrate                               # применить все (alembic upgrade head)
docker compose run --rm migrate alembic downgrade -1          # откатить последнюю
docker compose run --rm migrate alembic current               # текущая версия схемы
```

Новая миграция после изменения моделей в `backend/app/storage/sqlalchemy/tables.py`:

```
docker compose --profile test up -d db-test
cd backend
export DATABASE_URL=postgresql+asyncpg://keitaro:keitaro@127.0.0.1:55432/keitaro_test
uv run alembic upgrade head
uv run alembic revision --autogenerate -m "что изменилось"    # прочитать и поправить файл
uv run alembic check                                          # модели и миграции совпадают
```

## Разработка

Контракт: `contracts/scripts/generate.sh` после правки `schema.graphql`, `contracts/scripts/check.sh` для проверки.

| | backend | frontend |
|---|---------|----------|
| Зависимости | `uv sync` | `corepack pnpm install` |
| Запуск | `uv run uvicorn --factory app.main:create_app --reload` | `corepack pnpm dev` |
| Тесты | `uv run pytest -q` | `corepack pnpm test` |
| Линтеры | `uv run ruff check . && uv run ruff format --check .` | `corepack pnpm lint` |
| Типы | `uv run pyright` | `corepack pnpm typecheck` |

Сквозные сценарии S1–S8 из ТЗ идут в браузере на всём сервисе; Keitaro заменён поддельным трекером `backend/tests/fake_tracker.py`, в настоящий ничего не пишется:

```
cd frontend
corepack pnpm exec playwright install chromium    # один раз
corepack pnpm test:e2e
```

Тесты хранилища, шины и кэша на настоящих базах, брокере и Redis (без них пропускаются с причиной, в CI пропуск запрещён):

```
docker compose --profile test up -d --wait db-test mongo-test rabbitmq-test redis-test
export TEST_DATABASE_URL=postgresql+asyncpg://keitaro:keitaro@127.0.0.1:55432/keitaro_test
```

### Нагрузочный сценарий

Работает на стеке с поддельным трекером; настоящий Keitaro и ключ из `.env` в нём не используются.

```
docker compose -f compose.yaml -f compose.load.yaml up --build -d --wait --scale worker=2
cd backend && uv run python -m scripts.load          # адреса и размеры — в --help
docker compose -f compose.yaml -f compose.load.yaml down -v
```

Сценарий через BFF готовит черновики, одновременно ставит публикации и создания кампаний, каждый запрос повторяет с тем же `taskId`, на 1,5 секунды включает сбой трекера и ждёт конца всех задач. Он завершается с ошибкой, если задача не завершилась, появилась лишняя задача или кампания, сумма долей потока в трекере не 100 или в outbox остались сообщения (R-OPS-06).

Прогон 17.11.2026 на машине разработчика, 200 публикаций и 100 созданий, по 25 запросов одновременно; нарушений нет:

| Обработчиков | Сбой трекера | Задач | Отклонено | Время, с | Задач в секунду | Медиана, с | 95-й перцентиль, с |
|---|---|---|---|---|---|---|---|
| 2 | 1,5 с | 300 | 0 | 4,7 | 64 | 0,63 | 2,73 |
| 2 | нет | 300 | 0 | 4,7 | 64 | 0,36 | 0,55 |
| 4 | нет | 300 | 0 | 4,6 | 65 | 0,34 | 0,56 |

Время задачи — от постановки до итога по отметкам сервера. Четыре обработчика не быстрее двух: в этом прогоне скорость ограничена постановкой задач, а не обработкой.

После того как процесс, записавший сообщение, стал сам сразу отправлять его в шину (R-EV-03), те же прогоны с двумя обработчиками:

| Сбой трекера | Задач | Отклонено | Задач в секунду | Медиана, с | 95-й перцентиль, с |
|---|---|---|---|---|---|
| 1,5 с | 300 | 0 | 63 | 0,19 | 2,32 |
| нет | 300 | 0 | 58 | 0,12 | 0,26 |

Медиана без сбоя упала с 0,36 до 0,12 с: раньше сообщение ждало опроса outbox отдельным отправителем (раз в 0,5 с). С остановленным отправителем задачи выполняются так же. При остановленном RabbitMQ запрос отвечает сразу, задача ждёт и выполняется после запуска брокера — в проверке через 27 с, когда истекла аренда захваченной строки outbox (30 с).

Приём задач ограничивал один веб-процесс бэкенда: под нагрузкой он занимал одно ядро на 97 %, остальные простаивали. Число процессов задаётся `WEB_CONCURRENCY` (в compose по умолчанию 2). 400 публикаций и 200 созданий, два обработчика, без сбоя трекера, каждый прогон на чистой базе:

| Веб-процессов | Задач | Отклонено | Задач в секунду | Медиана, с | 95-й перцентиль, с |
|---|---|---|---|---|---|
| 1 | 600 | 0 | 61 | 0,08 | 0,22 |
| 2 | 600 | 0 | 106 | 0,08 | 0,15 |
| 4 | 600 | 0 | 180 | 0,08 | 0,23 |

Между прогонами стек снимается с томами (`down -v`): поддельный трекер при перезапуске выдаёт те же ID заново, и на сохранённой базе новые кампании с ними столкнутся.

### Хранилище

`STORAGE_BACKEND` в `.env` выбирает реализацию; сервисы и GraphQL от неё не зависят, все адаптеры проходят один набор тестов (`backend/tests/storage/`).

| Значение | Что нужно | Запуск |
|----------|-----------|--------|
| `postgres` (по умолчанию) | Postgres, миграции Alembic | `docker compose up --build` |
| `mongo` | MongoDB одним узлом replica set (нужен транзакциям), индексы создаются при старте | `STORAGE_BACKEND=mongo docker compose --profile mongo up --build` |
| `memory` | ничего, данные живут до перезапуска | — |

### Защита API

- Браузер обращается только к `/api/*` своего сервера; адрес бэкенда и ключ Keitaro в него не попадают.
- Бэкенд наружу не опубликован (в `compose.yaml` у него нет проброса порта).
- GraphiQL и интроспекция схемы включаются только при `DEBUG=true`; запрос ограничен по числу лексем и псевдонимов.
- Ключ Keitaro читается из окружения и хранится как секретное значение: в печати настроек его нет.

Проверено вручную на запущенном стеке 17.11.2026: интроспекция отклонена, GraphiQL отвечает 404, запрос с 16 псевдонимами и запрос длиннее 1000 лексем отклонены, порт бэкенда не опубликован, ключа нет ни в журналах контейнеров, ни в ответах интерфейса. Сканером уязвимостей API не проверялся.

Хуки перед коммитом (линтеры, поиск секретов, формат сообщения):

```
uvx pre-commit install
```
