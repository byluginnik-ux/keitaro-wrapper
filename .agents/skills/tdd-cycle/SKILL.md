# Цикл разработки от тестов

## Шаги

1. **Требование.** Найти номер `R-xx` или сценарий `Sx` в `docs/SPEC.md`. Имя теста пересказывает требование словами: `test_removed_offer_gets_zero_share`, а не `test_recalc_2`.
2. **Красный.** Написать тест, запустить, убедиться, что он падает по ожидаемой причине (утверждение, а не ошибка импорта). Для нового модуля допустима заглушка с `raise NotImplementedError`, чтобы тест дошёл до утверждения.
3. **Коммит теста:** `test(<часть>/<область>): <что проверяется>`. Тест в этом коммите красный — это нормально и видно в истории.
4. **Зелёный.** Минимальная реализация, от которой тест проходит. Ничего сверх теста.
5. **Коммит реализации:** `feat(...)` или `fix(...)`. После него весь набор тестов и линтеры зелёные.
6. **Рефакторинг** — отдельным коммитом `refactor(...)`, тесты не меняются и остаются зелёными.

## Что считается хорошим тестом

- Проверяет поведение через публичный вход (функция сервиса, мутация GraphQL, маршрут BFF, компонент), а не внутреннее устройство.
- Один тест — одна причина упасть.
- Данные сценариев берутся из SPEC.md: те же офферы A, B, C, D и те же числа.
- Внешние системы подменяются на границе: HTTP Keitaro — в бэкенде, GraphQL бэкенда — в BFF.

## Ошибка в готовом коде

Сначала тест, воспроизводящий ошибку (`test(...)`), затем исправление (`fix(...)`). Если ошибка в самом требовании — сначала `docs(spec): …`.

## Команды

```
cd backend  && uv run pytest -x -q
cd frontend && pnpm test
```
